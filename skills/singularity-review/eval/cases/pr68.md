# Case: example-org/platform-charts#68 — otel-agent chart

## Why this case exists

This is the first eval case with **confirmed ground truth from a real cold-start VERIFY run**, not hand-derived. It is also the run that measured the cost problem this fix addresses: 8 spawns (4 FIND + 4 VERIFY, one chunk only) cost ~470,000 subagent tokens — roughly 63% of a 5-hour session — and the review was still incomplete (chunk 2 never ran, several FIND candidates never reached VERIFY). Two things caused most of that cost, and both are exactly what this round of changes targets:

1. `paranoid` disabled the role prefilter, spawning `backend-engineer` on a chart with no Go/Python code — 58k tokens for one P3.
2. There was no way to see the cost coming — spawn count (8) looked cheap; token count (470k) was not.

This case is the regression baseline for both fixes. Re-run it after any change to the prefilter or the token-ceiling logic and compare against the ground truth below.

## Known defects (ground truth — cold-start CONFIRMED)

1. **[P1]** ClusterRole grants `nodes/proxy` cluster-wide with no configured consumer — `charts/otel-agent/templates/rbac.yaml:35`. Confirmed mechanism: `get` on `nodes/proxy` authorizes the apiserver's kubelet-exec proxy path (`/api/v1/nodes/<node>/proxy/exec/...`) — container exec on any node, from the collector's SA token. Confirmed the pipeline doesn't need it: `scrape_configs: []`, targets arrive as direct endpoints from the target allocator, no apiserver-proxy relabel config anywhere in the rendered output. `nodes/metrics` (the subresource kubelet scraping actually needs) is granted separately and is correct.
   - Caught by: platform-engineer (FIND) → adversarial-verifier CONFIRMED, `clean`.

2. **[P1]** Stock chart defaults render and apply successfully but produce a permanently non-functional exporter — `charts/otel-agent/values.yaml:26-33`, `templates/_helpers.tpl:98`. Confirmed against the actual pinned collector image (v0.156.0): the collector reaches `Running`/ready (does *not* crash, contrary to the initial finder's mechanism claim — `url.Parse` accepts the malformed relative endpoint), then retries every export forever (`unsupported protocol scheme ""`). Credentials render as `base64(":")`. No `required` guard, no `values.schema.json` exists (9 of 15 other charts in the repo have one). `NOTES.txt` warns but the warning is invisible under GitOps (`helm template` output has zero `WARNING` lines — ArgoCD never runs `helm install`, never sees NOTES). CI never catches this because `ci/test-values.yaml` supplies a valid endpoint — the stock-defaults path is never exercised.
   - Caught by: backend-engineer, devops-sre, platform-engineer (3 independent FIND roles — a real convergence signal) → adversarial-verifier CONFIRMED, `clean`.

3. **[P2]** `serviceAccount.create=false` with no explicit name binds cluster-wide RBAC to the namespace's `default` ServiceAccount, and separately targets a target-allocator ServiceAccount that nothing creates — `charts/otel-agent/templates/_helpers.tpl:63`, `templates/rbac.yaml:23`. Confirmed via render (`--set serviceAccount.create=false`): both ClusterRoleBindings gate only on `rbac.create`, never on `serviceAccount.create`. Confirmed against operator v0.156.0 source that the operator will not self-provision the allocator SA when the chart sets `spec.targetAllocator.serviceAccount` (which it always does) — so the dangling reference is a hard `Forbidden` failure, not theoretical. Verifier corrected the finding's overstated "BYO-SA is entirely unusable" claim (it works if you also name+create the derived `-targetallocator` SA) and flagged the obvious-looking fix (gate the bindings on `serviceAccount.create`) as net-negative — it would break legitimate BYO-SA users needing the binding. Correct minimal fix: `fail` when `create=false` and `name` is empty, not a gate on the binding.
   - Caught by: platform-engineer, solutions-architect, backend-engineer (3 independent FIND roles) → adversarial-verifier CONFIRMED, `clean`.

## Known non-defects (must NOT be reported as findings)

1. **`targetAllocator.prometheusCR.allowNamespaces` doesn't narrow the ClusterRole.** Mechanically true (verified: identical ClusterRole hash whether `allowNamespaces` is set or not) — but `README.md:60-64` explicitly documents the grant as cluster-wide, states the reason (informers start unconditionally regardless of discovery scope), and tells operators to scope it manually if needed. This is a **documented tradeoff**, not a trap — a reviewer flagging this as "a knob that misleads the operator" is wrong; the operator was told. Verdict: `borderline` KILL (mechanical claim correct, but the documentation coverage makes it not a defect). Note for future runs: `docs/internal-components.md:19-20` ("cluster-wide RBAC requires a separate security review") cuts the other way as org policy and is worth a security-review-record check independent of this specific finding.

2. **The double `b64enc` in `templates/secret.yaml`** (`otel-agent.basicAuth | b64enc`) is correct, not a double-encoding bug — two independent FIND roles checked this and confirmed it: the helper produces `base64(user:pass)` (the actual HTTP Basic-auth token value), and the Kubernetes Secret `.data` field requires one additional outer base64 layer for storage. A reviewer flagging this without decoding both layers would produce a false positive.

## Scoring notes

- **Recall this run:** 3/3 confirmed defects found (but only within the one chunk reviewed — `otel-operator` was never scoped, so this is not evidence the *full* PR would recall everything).
- **False positives:** 1 candidate (`allowNamespaces`) correctly killed at VERIFY rather than reaching REPORT — this is the two-phase architecture working, not a failure.
- **Tier:** correctly selected `paranoid` under both the old and new RBAC signal table, but for the right reason under the new one (a genuine cluster-wide privilege-escalation grant, not merely "a file named rbac.yaml exists" — see the sibling case this replaced the old signal's failure mode on).
- **Cost — the actual finding of this run:** 8 spawns, ~470k tokens, ~63% of session, incomplete. This number is why the token-ceiling and paranoid-prefilter fixes exist. **Re-run this exact case after those fixes land and record the new total here** — that comparison is the direct evidence of whether they worked, not reasoning about them.
- **Not yet measured:** whether preserving the prefilter at `paranoid` would have dropped `backend-engineer` for this chunk. It should not have — this chunk's defects (2) and (3) were both independently caught by backend-engineer, and its role-relevance signal (secret handling, config-as-contract) is real for this chart even without literal Go/Python. Re-running should confirm backend-engineer still spawns here (correctly) while checking whether a *different*, genuinely-irrelevant chunk drops a role it shouldn't have needed.
