# Case: example-org/platform-charts#99 — cluster-readiness GPU modes

## Why this case exists

This is the **A/B measurement case** for the cost-architecture work. It was reviewed once at baseline, then re-run with Changes 2 (shared evidence pack) and 4 (trimmed agent files) applied — same PR, same head SHA, same two roles, same tier. It is the only case with a controlled before/after on the same target.

## Known defects (ground truth)

Confirmed across both runs, self-verified against the actual chainsaw script:

1. **[P2]** Allocation-observation window remains race-prone — `tests/12-gpu/chainsaw-test.yaml:166,180-195`. Probe pod sleeps exactly 2s then exits; loop polls every 1s with two sequential `kubectl` round-trips per cycle. Under API latency an iteration can observe `Succeeded` before capturing an allocation, hitting the hard failure `"deallocated before its allocation could be observed"`. This PR tightened the poll 5s→1s but did not widen the margin. **Fails loudly (flake), never a silent pass.**
2. **[P2]** Shared `deadline` across both wait loops yields a misleading timeout message — `tests/12-gpu/chainsaw-test.yaml:178,229,236`. One deadline computed at line 178 bounds both loops; the second loop's failure text still reports the full `GPU_PROBE_TIMEOUT_SECONDS` regardless of how much the first loop consumed.

Found **only in the post-change run** (see Confound below before attributing this to the changes):

3. **[P2]** `clusterPolicySeparateDRA` silently assumes the DRA controller lives in `operatorNamespace` — `templates/rbac.yaml:439-448`, `tests/12-gpu/chainsaw-test.yaml:17`. No `draControllerNamespace` key exists anywhere in values, schema, or templates. A real `nvidia-dra-driver-gpu` install in its own namespace passes schema, passes `helm lint`, passes both CI render corners, then fails the gate Job on a real cluster with a misleading *"GPU Operator Deployment is not ready"* message naming a namespace/name pair that was never supposed to exist there. Fail-closed (no security/data impact); cost is a blocked gate diagnosed at the most expensive point.
4. **[P3]** The 2×2 mode matrix has four legal corners; CI positively renders only two — `validate.yml:210-228`, `ci/platform-alternate-values.yaml`. The overlay flips *both* axes together, so `externalSecret + clusterPolicySeparateDRA` (a plausible real topology) is never rendered positively.

## Known non-defects (must NOT be reported)

1. **The 6 kube-score CRITICALs** (image pull policy, NetworkPolicy, ephemeral storage, security context ×2, container resources) are **pre-existing on `origin/main`** with identical count and content. Verified by rendering `origin/main` with the same values file. Reporting these against this PR is a baseline-attribution error.
2. **The trivy `KSV-0053` `pods/exec` hit** at `rbac.yaml:18-20` — same: pre-existing baseline, different Role, different stage.
3. **The schema requiring the new mode keys is a breaking change, but an intentional one** — README explicitly instructs setting both modes explicitly, and `values.yaml` ships defaults. A reviewer flagging this as an accidental compatibility break is wrong; it's a documented design choice.
4. **`ci/platform-alternate-values.yaml` rendering "wrong" standalone** — it is an *overlay* with no `stage:` key, and CI always layers it on `platform-values.yaml` (`validate.yml:213-223`). Rendering it alone yields `stage=kubernetes` and is not a valid alternate-mode test. An evidence pack that renders it standalone is feeding bad evidence — this was caught and corrected during pack construction.

## Measurement: baseline vs Changes 2 + 4

Same PR, same head, same 2 roles (`platform-engineer` + `backend-engineer`), same `default` tier.

| Role | Baseline tokens / calls | Post-change tokens / calls | Δ tokens | Δ calls |
|---|---|---|---|---|
| platform-engineer | 68,870 / 11 | 55,931 / 5 | **−18.8%** | −55% |
| backend-engineer | 64,634 / 36 | 67,553 / 17 | **+4.5%** | −53% |
| **Total** | **133,504** | **123,484** | **−7.5%** | −52% |

**Projected in the design doc: 15-25%. Actual: 7.5%.** The projection was wrong, and the reason is recorded below rather than smoothed over.

### The negative result and its cause

`backend-engineer` got **more expensive** while halving its tool calls. Cause: both agents were instructed to *"read the pack"*, so each pulled the full ~70KB (~17k tokens) into context immediately. Once read, the pack is re-billed on every subsequent turn.

The economics are asymmetric:
- **Benefit** ∝ turns eliminated.
- **Cost** ∝ pack size × turns remaining after the read.

`platform-engineer` amortized a 17k pack over 5 turns → large net win. `backend-engineer` carried the same 17k across 17 turns → carrying cost exceeded the ~19 calls it saved.

This is an **implementation error, not a design flaw** — SKILL.md already specified "compact summary inline, path to `Read` on demand." The spawn prompts contradicted the skill's own instruction. Fixed in SKILL.md with the measured numbers attached so the failure mode is explicit rather than inferable.

**Re-measure after the fix before trusting any revised projection.** The corrected form (summary inline, pack as on-demand pull) has *not* been measured.

### Confound on the recall improvement

The post-change run found two findings the baseline missed (#3, #4 above) — but the improvement **cannot be cleanly attributed to the evidence pack**. The post-change spawn prompt also told the agent *"a prior pass already found the race and deadline items — spend effort on what wasn't covered."* That redirect alone plausibly accounts for finding new ground.

The token/tool-call deltas are clean measurements. **The recall delta is confounded and must not be cited as evidence the pack improves recall.** Isolating it needs a run with the pack but without the redirect.

## What to watch on the next re-run

- Does the corrected pack usage (summary inline, pack pulled on demand) beat 7.5%? That is the actual test of Change 2.
- Does `platform-engineer` still find defect #3 without the "prior pass found X" redirect? That isolates the recall question.
- Do defects #1 and #2 still surface? They are the stable regression anchors — losing either signals a real recall regression.
